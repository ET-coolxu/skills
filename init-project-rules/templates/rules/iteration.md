# 需求迭代

新版本或范围变化落地时，同一轮把规则和说明改完。不要只改需求文档，也不要只改代码。

## 何时更新

出现以下任一情况就要更新：

- 新增 `docs/需求/` 下的新版本需求，或用户要求按新版本实现
- 修改现有需求的「本期要做 / 本期不做」
- 实现时发现某条规则仍在禁止已经纳入本期的能力

先读 `docs/需求/` 里版本最新的一份，以它为当前范围。更早版本里「不做」的条目，新需求写了要做，就不再禁止。

## 改哪里

| 变化 | 更新 |
| --- | --- |
| 当前版本、本期不做 | `.cursor/rules/project.mdc` 的「范围」 |
| 分层约定 | {{SCOPED_RULES}} |
| 目录、行为、规则表 | `docs/架构/项目架构.md` |
| 一句话现状 | `README.md` 首段 |

工程约定保持不动：{{INVARIANTS}}

`docs/agent/` 的类型模板不在上表里。更新它们要先给出「提示词库建议」，用户确认后再写。见 `.cursor/rules/agent-prompts.mdc`。

新主题塞不进现有规则时，另建一个 `.mdc`（一件事、50 行以内），并在架构说明的规则表加一行。

## 例子

新版本要求一项过去禁止的行为时：删掉对应规则里的禁令，改成新行为。`project.mdc` 的当前文档改为新的需求文件，并去掉已经纳入本期的「本期不做」条目。
